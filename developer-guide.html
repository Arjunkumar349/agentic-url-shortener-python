1. Purpose and mental model

This repository contains two related pieces:

  1. A small URL shortener service that a developer can run locally. It creates short links, redirects requests, and records click totals in SQLite.
  2. A governed SDLC workflow prototype that takes one of three fixed requirements (greenfield, brownfield, or ambiguous) and creates a traceable, run-scoped engineering proposal with approvals, validation, documentation, and a release summary.

The workflow engine is the main demonstration of agentic-style coordination. The scenario handlers in this version are deterministic Python fixtures: they do not call Copilot, Claude, an LLM, or an external service. For the greenfield case, the implementation stage packages the checked-in URL-shortener source, tests, and API schema into the run's artifacts. It does not modify your working source tree.

Important distinction: successfully completing a workflow means the workflow stages completed. It does not mean the service was deployed or is production-ready. The summary deliberately reports “review_ready_not_deployed” for a well-defined scenario, and “blocked_pending_clarification” for the ambiguous one.

2. Understand the requirements before coding

Start with systemcontext.ini. It describes the overall assignment: transform a requirement into reviewable engineering work, reason about brownfield code, orchestrate sequential and parallel work, retain audit and decision history, require human approvals, validate outputs, and explain risks and limitations.

Then read README.md for the repository's current implementation decisions and setup. The shortener scenario calls for a service with:

  • An API to create a short link.
  • A redirect from a short code to the original HTTP(S) URL.
  • Per-link analytics, currently click count plus creation and last-access timestamps.
  • Persistent storage, input checks, and safe handling of short-code collisions.
  • Reliability considerations and explicit documentation of unspecified production requirements.

A practical requirement-reading checklist

  1. Extract actions and users. What should an API caller be able to create, retrieve, or observe?
  2. Turn nouns into data. A link has a short code, target URL, creation time, click count, and last access time.
  3. Write observable behavior. For example, a valid create request returns a short URL; visiting its code redirects and increments the count.
  4. Identify edge cases. Invalid schemes, malformed JSON, unknown codes, duplicate codes, large request bodies, and storage errors all need deliberate behavior.
  5. Separate requirements from assumptions. This brief does not set authentication, expiration, analytics retention/privacy, traffic targets, availability objectives, or deployment topology. The prototype documents these rather than pretending they were specified.
  6. Make uncertainty visible. In the ambiguous scenario, the workflow records questions and intentionally withholds service implementation until they are answered.

The scenario definitions live in agentic_sdlc/scenarios.py. The repository's overall requirement is in systemcontext.ini; the product API behavior is also documented in the README and described by the OpenAPI schema.

4. Understand the execution model

The CLI asks build_scenario for a task list, handler functions, and initial context. It creates a WorkflowState and passes both to WorkflowEngine. The engine checks that the dependency graph is valid, then repeatedly runs all ready tasks. A task is ready only when every dependency has succeeded.

understand
    ↓
decompose
    ↓
design
    ↓
[human design approval]
    ↓
implement
    ├──→ unit_validation ──┐
    └──→ documentation ───┴→ integration_validation
                                  ↓
                         [human release approval]
                                  ↓
                           release_readiness
  1. Understand: normalizes the scenario requirement, carries known ambiguity, and records available inventory evidence.
  2. Decompose: lists dependent work such as API contract, storage, implementation, tests, documentation, and release review.
  3. Design: records decisions and risks, including safety boundaries and assumptions.
  4. Design approval: pauses before implementation unless explicitly approved.
  5. Implement: emits a proposal. Greenfield packages the service source, tests, and API schema; brownfield emits an inventory-based change plan; ambiguous emits clarification questions and no service code.
  6. Parallel branches: static validation and documentation are independent tasks that can run in the same ready frontier.
  7. Integration validation: waits until both branches finish, then checks stage outputs and required greenfield deliverables.
  8. Release approval and readiness: request human approval, then create the final engineering summary and run metrics.

State, approvals, and failure handling

  • The run state tracks task statuses, outputs, attempts, artifacts, approvals/audit events, context, and timestamps.
  • Unapproved checkpoints save state and return paused_for_approval. Resume loads state.json and continues the same run.
  • Tasks may retry up to their configured attempt limit; implementation also has a fallback handler that produces a manual fallback plan.
  • Artifacts are confined to a task directory under the run directory, checked for unsafe paths and likely inline credentials, and not overwritten.
  • A terminal task or artifact-policy failure emits a safe-stop event and removes generated run artifacts (rollback); it does not undo source files because the workflow never edits them.
  • WorkflowEngine.replan() can replace a succeeded upstream output and invalidate that task's descendants, deleting their stale artifacts while leaving unrelated completed branches intact.

Audit events are appended to audit.jsonl. The final summary includes run-level success/retry/rollback metrics, mean recovery time where recovery occurred, and elapsed time at report generation. These are prototype run signals, not fleet-wide reliability statistics.

5. Set up the project and run tests

The project requires Python 3.10 or newer and has no runtime third-party dependencies. From the repository root, open PowerShell or a VS Code terminal:

cd C:\Apps\AgenticSWSystem
python --version
python -m unittest discover -s tests -v

If this project uses its local virtual environment, invoke its interpreter explicitly:

.\.venv\Scripts\python.exe -m unittest discover -s tests -v

The suite covers both the workflow engine and the URL-shortener service. A successful run ends with OK. Run it again after changes that affect a stage, policy, API, or persistence behavior.

Optional: install the project in editable mode to use the registered agentic-sdlc command:

python -m pip install -e .
agentic-sdlc --help

6. Run the three workflow scenarios

Run commands from the repository root. The examples use python -m agentic_sdlc, so editable installation is not required.

Greenfield: a new service

python -m agentic_sdlc run --scenario greenfield --approve all

This executes both approvals, packages the URL-shortener files into the run artifacts, validates generated Python syntax and JSON parsing, checks stage synchronization, and produces a release-readiness summary. To see the approval gates rather than approve immediately, omit --approve all.

Brownfield: reason about an existing workspace

python -m agentic_sdlc run --scenario brownfield --workspace .

By default this pauses at design approval. Provide the approval flags up front if you want the full proposal in one invocation:

python -m agentic_sdlc run --scenario brownfield --workspace . --approve all

The inventory is a bounded scan of up to 500 files, excludes common dependency/build directories, and uses filename keywords to suggest candidate review targets. It is not semantic code analysis and does not edit the selected workspace. Point --workspace at the codebase you want inventoried.

Ambiguous: surface questions instead of guessing

python -m agentic_sdlc run --scenario ambiguous --approve all

This scenario completes the governance/reporting flow but intentionally does not generate service code. Its release summary is blocked_pending_clarification. Approval of a workflow checkpoint is not approval to ignore unresolved product questions.

Pause and resume through approvals

Without approval flags, the initial run stops at design approval. The CLI prints a run ID and run directory. Copy the run ID shown in the output and resume using:

python -m agentic_sdlc run --scenario greenfield
python -m agentic_sdlc resume <run-id> --approve design
python -m agentic_sdlc resume <run-id> --approve release

Replace <run-id> with the printed ID. The run identifier is not literally the text in angle brackets. If you used a custom output folder, pass the same folder to each resume call with --output <folder>. The first paused invocation normally exits with code 2; that is the expected CLI signal for a saved approval pause, not an implementation failure. Completed runs exit 0; failed runs exit 1.

You can approve only one checkpoint at a time or both up front: repeat --approve as needed, for example --approve design --approve release, or use --approve all.

7. Run and use the URL shortener

The standalone service is separate from the workflow CLI. Start it in one terminal:

python -m url_shortener

It uses Python's built-in WSGI server, listens on 127.0.0.1:8000 by default, and creates a local url-shortener.sqlite3 database. The server is for local development, not a production deployment.

Create a short link from another PowerShell window:

$created = Invoke-RestMethod `
  -Method Post `
  -Uri http://127.0.0.1:8000/api/urls `
  -ContentType 'application/json' `
  -Body '{"url":"https://example.com/docs"}'
$created

Use the returned short_url in a browser or HTTP client. Each GET to the short URL returns a redirect and records a click. Read analytics using the returned code:

Invoke-RestMethod `
  -Method Get `
  -Uri "http://127.0.0.1:8000/api/urls/$($created.code)/stats"
Method and routePurposeTypical response
POST /api/urlsCreate a short URL. Send JSON with only a url field; the destination must be a valid absolute HTTP(S) URL.201 Created with code, short URL, target, and creation time.
GET /{code}Redirect to the original destination and increment click count.302 Found with a Location header; 404 for unknown/invalid codes.
GET /api/urls/{code}/statsRead per-link click analytics.200 OK with target, created time, clicks, last access; 404 if missing.
GET /healthBasic process health check.200 OK with {"status":"ok"}.

To change its local settings:

python -m url_shortener --host 127.0.0.1 --port 8080 --database .\data\urls.sqlite3

The same settings can be supplied through URL_SHORTENER_HOST, URL_SHORTENER_PORT, and URL_SHORTENER_DB.

8. Read a workflow run's outputs

By default, each run is stored in .agentic-runs/<run-id>/. The CLI prints the actual location. A completed run contains:

  • state.json — resumable workflow state, stage results, statuses, attempts, and artifact index.
  • audit.jsonl — append-only event records with timestamps, task transitions, approval events, retry/fallback outcomes, and safe-stop/rollback information where applicable.
  • artifacts/understand/, artifacts/decompose/, artifacts/design/, etc. — files produced by each stage.
  • artifacts/implement/ — greenfield service code/tests/schema, brownfield plan/contract, or ambiguous clarification documents.
  • artifacts/release_readiness/engineering-summary.md and engineering-summary.json — decisions, risks, validation, limitations, release status, and run metrics.

Artifacts are generated proposals, not files installed into your application or applied to the workspace. Review them and run their tests separately before adopting any change.

9. Make a change safely

  1. State the behavior you intend to change. Identify the relevant requirement, API response, workflow stage, or policy rule.
  2. Read the producer and its tests. For service changes, inspect url_shortener/service.py and tests/test_url_shortener.py. For scenario/workflow changes, inspect agentic_sdlc/scenarios.py, agentic_sdlc/orchestrator.py, and tests/test_orchestrator.py.
  3. Update the contract and documentation together. If a route or payload changes, update the OpenAPI schema and README/guides as appropriate.
  4. Add or adjust focused tests. Cover the success path, invalid input, not-found cases, and relevant failure/reliability behavior.
  5. Run the complete suite. Use python -m unittest discover -s tests -v.
  6. Exercise the matching workflow scenario. For example, run greenfield after changing emitted implementation artifacts, or brownfield after changing inventory/proposal behavior.
  7. Inspect artifacts and audit output. Confirm content is correctly scoped, no source was unexpectedly changed, approvals remain in the intended order, and summary risks are accurate.

When changing common orchestration behavior, retain the core guarantees: validated dependency graph, explicit approvals, bounded retries, artifact path and credential checks, durable pause/resume state, audit events, and safe-stop/rollback behavior.

10. Know the boundaries and next questions

  • The scenario handlers are deterministic fixtures, not autonomous model agents.
  • Brownfield reasoning is based on a bounded filename inventory, not symbol or call-graph analysis.
  • Generated Python is syntax-parsed and generated JSON is parsed; the orchestrator does not execute generated code. Run tests separately in a suitable environment.
  • The workflow's JSON state store is intended for a prototype and is not safe as a multi-process shared database. There is no distributed queue or deployment integration.
  • The service uses SQLite for a local single-instance prototype. It does not define production capacity, high availability, backups, migrations, or rate limiting.
  • The statistics API currently exposes target URLs and click counts without authentication. Use only in a trusted environment until access control and privacy needs are specified.
  • Authentication, link expiry, deletion, analytics retention, privacy requirements, redirect latency, traffic profile, and availability objectives are open product/operational decisions.
  • The WSGI development server is not a production server. Production deployment needs a deployment/runtime design, security review, observability, and operational testing.

Use the ambiguous scenario and final summary to record such questions rather than silently choosing production behavior. Humans remain responsible for design and release approvals.

Maintainer note: keep this guide aligned with the CLI, scenario graph, service API, tests, and README whenever those interfaces change.
